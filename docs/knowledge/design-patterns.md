# UI: сначала общепризнанные решения

Обязательное правило для **любой** реализации UI: экраны, компоненты, навигация, пустые состояния, формы, модалки, command palette, таблицы, настройки.

Правило агента: [`ved-ui-patterns.mdc`](./ved-ui-patterns.mdc) (зеркало `.cursor/rules/`). ADR **D32**. Индекс: [`design.md`](./design.md) · baseline D14 [`design-baseline.md`](./design-baseline.md) · backlog [`design-parity.md`](./design-parity.md).

## Принцип

Не изобретать интерфейс с нуля. Сначала искать решение в общепризнанных UI-паттернах и дизайн-системах, затем адаптировать под наш продукт.

Пользователь должен узнавать привычное поведение. Новизна допустима только если она упрощает задачу, а не ради оригинальности.

## Откуда брать решения (в таком порядке)

1. Уже существующие паттерны внутри этого репозитория (компоненты, layout, токены, copy).
2. Общепризнанные системы и эвристики:
   - Nielsen Norman — usability heuristics
   - WCAG — доступность
   - платформенные гайдлайны: Apple HIG, Material Design, Microsoft Fluent
   - устоявшиеся SaaS-паттерны: навигация, формы, таблицы, модалки, тосты, пустые состояния, поиск, Cmd+K
3. Референсы зрелых продуктов той же категории (Linear, Notion, Stripe, Figma, GitHub) — как паттерн, не как пиксель-в-пиксель копия.
4. Свой кастомный паттерн — только если пункты 1–3 не закрывают задачу.

## Как реализовывать

- Перед новым экраном или компонентом явно назвать паттерн: «это combobox», «это slide-over», «это empty state с одним CTA».
- Переиспользовать существующие компоненты, отступы, типографику, цвета, размеры. Не плодить второй button / modal / input.
- Сохранять предсказуемое поведение: фокус, Escape закрывает, Enter подтверждает, клик по overlay, loading, error, empty, disabled.
- Клавиатура и доступность не опциональны: focus visible, labels, достаточный контраст, не ломать Tab-порядок.
- Копирайт короткий и деловой. Не придумывать уникальные метафоры, если есть понятное слово («Сохранить», «Отмена», «Удалить»).

## Чего не делать

- Не копировать чужой бренд, иллюстрации, точные отступы и чужие фичи «потому что увидели у соседа».
- Не делать command palette, кастомные жесты, нестандартные меню и «умный» UI, пока базовые экраны и навигация не стабильны.
- Не вводить новый UI-паттерн в одном месте, если в проекте уже есть другой для той же задачи.
- Не объяснять отклонения фразой «так красивее». Нужна причина: доступность, платформа, ограничение домена.

## Если стандартный паттерн не подходит

В коде или в соседнем комментарии / PR / design note кратко зафиксировать:

- какой стандартный паттерн рассматривали;
- почему он не подходит;
- чем заменили.

Сознательные пробелы относительно конкурентов (например Cmd+K) не закрывать молча — смотреть [`design-parity.md`](./design-parity.md) и не тащить их в текущую реализацию без явной задачи.

## Определение готовности UI-задачи

Решение можно мержить, если:

- паттерн узнаваем без обучения;
- состояния default / loading / empty / error / success закрыты;
- поведение совпадает с уже принятым в проекте;
- нет нового визуального языка «только для этого экрана».
